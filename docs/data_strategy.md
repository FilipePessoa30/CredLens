## Target strategy

```text
public data + reproducible synthetic operational layer
```

**Public data** provides realistic structure, distributions, and (where available) real-world credit-risk relationships that a purely invented dataset couldn't credibly offer. **Synthetic data**, generated by documented, versioned code, fills in operational detail that public datasets typically don't expose at all — for example, day-to-day account-level delinquency-bucket transitions, a full collections-strategy history, or a portfolio-level time series long enough to build vintage curves. The two are combined deliberately, not blended silently.

### How synthetic and public data will stay distinguishable

Once implemented, this project will enforce (not just document) a separation:

- Synthetic tables/files will live under a dedicated path (e.g., `data/synthetic/`) and/or carry a `data_source` column with a value like `"synthetic"` vs. `"public:<dataset_name>"`, so any query or report can filter or label by provenance.
- Any generation script for synthetic data will be committed to the repository and runnable end-to-end, so every synthetic value is reproducible from code, not from a static file that could quietly drift from its generator.
- Documentation and any dashboard built later will state, next to any headline number, whether it derives from public data, synthetic data, or a blend — never presenting a synthetic value as an observed real-world outcome.

## Candidate source matrix

### Home Credit Default Risk (Kaggle)

- **Purpose**: Primary candidate for realistic application-level credit data (demographics, prior credit bureau history, application outcome, and default flag).
- **Coverage**: Application-level records with a binary default outcome; multiple related tables (bureau history, previous applications, installment payments) in the full competition dataset.
- **Granularity**: Application / loan-level.
- **Advantages**: Rich feature set, realistic joint distributions, widely used as a benchmark (comparable to other public analyses), large enough sample size for segment-level analysis.
- **Limitations**: A single snapshot in time, not a genuine longitudinal panel — does not natively support month-over-month portfolio evolution or vintage curves without synthetic extension; anonymized/obfuscated in ways that limit some interpretability; not representative of any specific real institution's current portfolio.
- **License to verify**: Kaggle competition data terms (varies by competition; must be read directly on the dataset's Kaggle page before download — not assumed here).
- **Leakage risk**: Known target-leakage pitfalls documented in the broader Kaggle community for this dataset (certain engineered features can leak default status); must be checked deliberately during the acquisition/audit phase, not assumed absent.
- **Fit for this problem**: Good fit for origination-level KPIs (approval-adjacent modeling, PD-style modeling); poor native fit for portfolio-over-time KPIs (vintage, roll rate, recovery) without a synthetic layer on top.
- **Decision pending**: Whether to use the full multi-table competition dataset or a lighter subset; confirm license terms before download.

### Other public credit-risk datasets (e.g., UCI/Statlog German Credit, Lending Club historical data, other Kaggle credit datasets)

- **Purpose**: Secondary/comparison candidates, or a fallback if the Home Credit dataset's license or leakage profile turns out to be unsuitable.
- **Coverage**: Varies by dataset — typically application or loan-level, some (e.g., historical peer-to-peer lending data) with partial repayment/status history over time.
- **Granularity**: Varies; generally loan-level.
- **Advantages**: Some (e.g., historical lending marketplace data) include loan status over time, which is closer to what portfolio/vintage analysis needs than a single snapshot.
- **Limitations**: Smaller and/or older than Home Credit; feature sets vary widely in richness; some well-known datasets (e.g., German Credit) are too small and too simplified for realistic segment-level analysis.
- **License to verify**: Varies by source; each candidate's license must be checked individually before use.
- **Leakage risk**: Unknown until reviewed individually.
- **Fit for this problem**: Case-by-case; would need individual evaluation against the KPI list in `docs/kpi_dictionary.md`.
- **Decision pending**: Not yet evaluated in detail; only tracked as a fallback category.

### Public macroeconomic indicators (e.g., central bank / national statistics series: unemployment, interest rates, inflation)

- **Purpose**: Contextual variables to explain portfolio-level trends that are driven by the macro environment rather than by the company's own decisions (e.g., a broad delinquency uptick coinciding with a rise in unemployment).
- **Coverage**: Country/region-level time series, typically monthly or quarterly.
- **Granularity**: Macro (national or regional), not loan-level — usable only as a joined context variable, not a primary table.
- **Advantages**: Genuinely longitudinal, official, well-documented, typically freely licensed for reuse.
- **Limitations**: No individual-level or loan-level signal by itself; only useful in combination with a portfolio dataset that has real time-series structure (public or synthetic).
- **License to verify**: Typically open/public-domain for official statistics, but the specific source's terms must still be confirmed and cited.
- **Leakage risk**: Low (aggregate, publicly known data), but must not be joined in a way that implies foresight the company wouldn't have had at decision time (a lookahead-bias risk in any forecast that uses it).
- **Fit for this problem**: Useful as a secondary, contextual layer once a primary portfolio dataset is selected; not a data source on its own.
- **Decision pending**: Which specific series and source to use; deferred until the primary dataset is chosen.

### Reproducible synthetic operational data

- **Purpose**: Fill the structural gap that public snapshot datasets leave — genuine month-over-month portfolio evolution, delinquency-bucket transitions, and collections-strategy outcomes — needed for vintage, roll-rate, cure-rate, and recovery-rate analysis.
- **Coverage**: Whatever the generation script is designed to produce; scope to be defined when this phase starts, informed by the public dataset(s) actually selected.
- **Granularity**: Designed to match loan-level, time-indexed granularity.
- **Advantages**: No licensing risk, no privacy risk, fully reproducible, can be shaped precisely to exercise every KPI in `docs/kpi_dictionary.md` (including the ones public snapshot data can't support).
- **Limitations**: Not real-world evidence — cannot be used to claim anything about real credit-risk relationships; only as realistic as the assumptions coded into its generator, which must be documented alongside it.
- **License to verify**: N/A (project-authored code); MIT license applies (see root `LICENSE`).
- **Leakage risk**: N/A in the traditional sense, but a poorly designed generator could bake in unrealistic, trivially-separable patterns that would make any later model look artificially good — a risk to guard against during design, not during data collection.
- **Fit for this problem**: Necessary complement to public data for this project's full KPI scope; not a substitute for it.
- **Decision pending**: Generation methodology and validation approach (e.g., how its distributions will be checked for plausibility) — to be designed when the data acquisition phase starts.
