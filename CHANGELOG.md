# Changelog

All notable changes to this project are documented in this file. Format loosely follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [0.7.0] - 2026-07-26

### Added — Credit Portfolio Intelligence: warehouse hardening + reproducible analysis layer (Phase 6)

- **Gate A - exact-cents monetary reconciliation** (`credlens.warehouse.reconciliation`): the prior `max(0.01, 0.1% of expected)` tolerance was wide enough to mask a material discrepancy on a large balance. Replaced with exact integer-cent equality: every monetary value on both the independent Python side and the SQL side is converted via `decimal.Decimal(str(value)).quantize(Decimal('0.01'), rounding=ROUND_HALF_UP)` - verified empirically to match DuckDB's own `CAST(x AS DECIMAL(18,2))` rounding exactly (round-half-away-from-zero on the decimal string, sidestepping both Python's banker's-rounding `round()` and float64 representation error). Achievable exactly, not just approximately, because the staging layer casts every monetary column to `DECIMAL(18,2)` once and every downstream `SUM` is exact decimal addition. Two new checks added (`paid_amount`, `scheduled_amount`), bringing reconciliation to 8 independently re-derived KPIs. Mandatory negative test (`TestOldToleranceRuleWasInsufficient`): a discrepancy engineered to pass the old percentage rule that fails the new exact-cents rule.
- **Gate B - structural test-root isolation** (`credlens.generation.testing_support`, new module): tests that generate data or build a warehouse now do so under an isolated `tmp_path`-rooted directory (`isolated_output_dirs`, `isolated_manifest_dir`), never the shared `data/synthetic/`/`data/warehouse/` roots an official demonstration run/suite/build occupies - fixing a real, previously-latent bug where a test using the same `scenario=baseline, scale=smoke, seed=2026` coordinates as an official demo run would legitimately recreate-then-delete that exact directory. `with_output_dirs()` (new, `credlens.generation.config`) makes this a genuinely different `generation_run_id` too, since output paths are part of the hashed config payload. `safe_rmtree`/`delete_exact_run_dir` give tests an allowlist-based (`PROTECTED_ROOTS`) cleanup path that structurally cannot delete outside its own authorized root, even given an adversarial relative path. 16 new tests prove: isolation holds, the official suite survives a colliding-coordinate test run, cleanup functions reject unauthorized roots, and paths cannot escape the allowed root.
- **Gate C - raw source integrity re-verification** (`credlens.warehouse.integrity`, new module): the raw layer's DuckDB views re-read parquet from disk on every query, so a file mutated after a build could previously change what every downstream query saw with nothing in the build's own manifest ever having been wrong. `verify_build_sources()` re-checks file existence/size/row-count/the generator's own `canonical_table_hash` (recomputed) plus the run's own manifest status/validation/version fields, called first by `credlens warehouse query`, `reconcile`, and `credlens.analysis.validation.validate_build_for_analysis` - raising `RawIntegrityError` and refusing to proceed on any mismatch. Chosen architecture (external views + mandatory verification, documented and justified over immutable materialization) - see `docs/warehouse_architecture.md`'s Raw Materialization Trade-off section. Mandatory negative test: mutate a parquet file after the build, confirm detection, confirm both reconciliation and named queries are blocked.
- **Two remaining KPIs implemented**, moving `warehouse/kpi_catalog.yml` to 0 `proposed` entries (59 total: 53 `implemented`, 6 `not_supported`): `scheduled_amount_due_this_month` (`mart_portfolio_monthly`, rewritten with `stock`/`payment_flow`/`scheduled_flow` CTEs) is period-scoped to each snapshot's own calendar month - never the whole future amortization schedule summed into one row - with principal/interest/fees breakdown and `paid_to_scheduled_ratio`; `mart_macro_stress_pre_post` (new mart) compares baseline vs. `macroeconomic_stress` split at the shock date derived from `fct_macro_monthly.is_synthetic` (not a hardcoded config value), with a new singular test (`assert_pre_shock_period_identical_across_scenarios.sql`) proving the pre-shock period is exactly identical between the two runs.
- **`credlens.analysis`, a new reproducible portfolio-analysis package** (`src/credlens/analysis/`, optional `analysis` extra - `matplotlib` only): `validation` (re-gates a build - tests passed, sources unmutated, fingerprint present - before anything else touches it), `metrics` (13 SQL-first query functions - mart wrappers plus 3 new segmentations: funnel by channel, portfolio by region×channel, approval rate by policy version; `MIN_SEGMENT_OBSERVATIONS=10` suppression flag, never silent row-dropping), `scenarios` (`composition_vs_performance` - splits a policy scenario's booked population into shared/baseline-only/scenario-only by `application_id`, separating the mechanical/composition effect from the performance effect on the shared population), `multiseed` (wraps Phase 4B's `run_monte_carlo`, labels every result `"simulation_variability_across_synthetic_dgp_seeds"` - never a confidence interval), `benchmark` (profiles already-acquired public datasets, kept strictly separate from any synthetic build, degrades to `[]` gracefully when files are absent), `charts` (12 chart functions, Okabe-Ito colorblind-accessible palette, a "Synthetic data" watermark on every figure), `provenance` (the analysis manifest - build identity, source/table/figure content hashes, the exact `run_analysis()` parameters used, warnings, status), `reporting` (bilingual EN/PT-BR executive summary built from "decision cards" - question/evidence/interpretation/decision-it-could-support/risk-limitation - and a technical report; every number is formatted directly from a DataFrame/dict the same run computed, never hand-typed), and `runner` (`run_analysis()` - orchestrates all of the above into one call). See `docs/analysis_architecture.md`.
- **`credlens analysis` CLI group**: `validate`, `run` (`--output-dir`, `--force`, `--no-benchmark`, `--multiseed [--multiseed-seeds/-scenario/-scale]`), `scenarios`, `benchmark`, `status`, `reproduce` (re-runs the same build_id with the same recorded parameters into a separate directory and verifies every table/figure content hash matches exactly). Every subcommand supports `--json` and a proper exit code; `run` refuses to silently overwrite an existing output directory.
- **`analysis/questions.yml`**: a versioned, 20-question business-question registry across 7 categories (credit funnel, portfolio composition, delinquency, vintages, cure/relapse, collections/recovery, scenarios), each with stakeholder, decision supported, KPIs/models/segmentations used, temporal window, maturity criteria, limitations, status, and a pointer to the exact function/table/figure that answers it. `analysis/specifications/segmentation_policy.md` documents the permitted segmentation attributes and the minimum-sample rationale.
- **`notebooks/credit_portfolio_case_study.ipynb`**: a thin, read-only viewer over `reports/portfolio_analysis/` - loads tables/figures and narrates them, never recomputes a query. Its code cells were verified to execute correctly against real analysis output (with `IPython.display` stubbed, since no Jupyter kernel/`nbconvert` is installed in this environment by deliberate choice - see `docs/analysis_architecture.md`'s own Limitations section for the exact honesty boundary of that verification).
- **A real official analysis run** produced `reports/portfolio_analysis/` (13 tables, 12 figures including a real multi-seed sweep, bilingual executive/technical reports, a complete provenance manifest) from `SUITE_sample_2026`.
- **97 new tests** across 10 new test files (`test_analysis_validation`, `test_analysis_metrics`, `test_analysis_scenarios`, `test_analysis_benchmark`, `test_analysis_charts`, `test_analysis_provenance`, `test_analysis_reporting`, `test_analysis_runner`, `test_analysis_multiseed`, `test_cli_analysis`, `test_analysis_metamorphic`, `test_kpi_catalog`), including the required metamorphic properties: row-reordering never changes a canonical content hash, duplicating an event table never changes a stock metric, a far-future installment never changes the current period's scheduled-due amount, a future snapshot never changes historical results, tampering blocks analysis validation, and running the same analysis twice produces byte-identical table/figure content hashes.
- CI (`.github/workflows/ci.yml`) extended with a full `credlens analysis` validation pass: a smoke-scale suite build, `analysis validate`/`run [--no-benchmark]`/`scenarios`/`status`/`benchmark`/`reproduce`, figure/manifest checks, and an explicit proof that the official `reports/portfolio_analysis/` is never touched by CI's own run. Real multi-seed sweeps and the public-dataset benchmark's external files remain out of CI by design.
- A real, previously-undetected bug found and fixed while writing `test_kpi_catalog.py`: `warehouse/kpi_catalog.yml` had two YAML syntax errors (an unquoted value beginning with `>`, parsed as a folded block scalar; an unquoted value containing a bare `: `, breaking block-mapping parsing) that had gone unnoticed because no code actually parses this file at runtime - it is documentation, referenced only in a docstring. Fixed, and a new structural test now guards against regression.
- Two other real bugs found and fixed while building this layer: `mart_writeoff_recovery` (and its upstream `stg_write_off_events`/`stg_recovery_events`/`int_write_off_recovery`) never propagated `suite_id`/`scenario`/`seed`/`scale`, breaking any query that needed to filter this mart by suite; `credlens analysis reproduce` did not replay the original run's `include_benchmark`/`include_multiseed` parameters, so reproducing a `--no-benchmark` run would spuriously add a benchmark figure and report a false mismatch - fixed by recording `parameters` in the provenance manifest itself and replaying them.
- A real, previously-undetected Gate B gap found while adding `tests/test_analysis_multiseed.py`: `credlens.generation.montecarlo.run_monte_carlo` (Phase 4B) calls `generate_suite()` once per seed without ever passing a `manifest_dir` override, so every multi-seed sweep (including `credlens analysis run --multiseed` and the pre-existing `tests/test_cli_synthetic_4b.py::test_monte_carlo_two_seeds`) wrote a suite manifest into the shared, git-tracked `reports/synthetic_validation/suites/` directory with no test cleaning it up - the existing monte-carlo test's own cleanup only ever deleted `monte_carlo_summary.json`, missing the per-seed suite manifest entirely. Fixed by adding exact, uniquely-seeded cleanup (never a directory-wide delete) to every test that exercises this path.

### Explicitly not included in this phase

Power BI/Tableau/Streamlit, any classification/regression/scorecard model, SHAP or fairness analysis, cutoff optimization, profit/ROI/LGD/EAD/regulatory-PD calculations, real causal inference, a definitive credit-policy recommendation, cloud deployment, and no commits/pushes - see `docs/roadmap.md`.

## [0.6.0] - 2026-07-25

### Added — Delinquency semantics correction and DuckDB + dbt analytical warehouse (Phase 5)

- **Cure semantics correction (a DGP behavior change, not a bug fix)**: curing arrears now pays only the overdue backlog as of the cure event's own month-end (`due_dates[i] < month_end`), never the full remaining contract balance. A cured contract's future, not-yet-due installments continue on schedule; a cured contract can become delinquent again later (relapse), which is now genuinely producible and was proven with 2 real relapsing contracts from an actual `contract_coverage` run, inspected month-by-month. Prepayment (paying off the entire remaining balance, including future installments) is now a distinct, explicitly typed event from cure - `payments.payment_type` (`scheduled`/`partial`/`cure`/`prepayment`) is a new required column (`contracts/operational/payments.yaml` version 1 -> 2). Relapse is derived, not stored: reconstructable from `account_monthly_snapshots.status`'s own time series, with no new redundant operational column. See `docs/adr/0010-cure-semantics-and-relapse.md`.
- Because this changes the generator's actual behavior (not just its code), old canonical hashes were deliberately NOT preserved: `GENERATOR_VERSION` bumped `0.5.0` -> `0.6.0` (recorded per-run in `generation_runs.generator_version`), every `config/synthetic/*.generation.yaml`'s `version:` field bumped `1` -> `2` (part of the hashed config payload, so `config_hash`/`generation_run_id` changes even where no parameter value changed), and `contract_version_set` moved `"phase4a-v1"` -> `"phase5-v1"`. Old runs/manifests are untouched and remain legible; new runs land in new, distinct directories - nothing was silently overwritten or mixed across generator versions.
- `contract_coverage` now produces 13 of 13 target rare states (was 12/13 in Phase 4B, with delinquency relapse as the one documented architectural gap) - proven via a real fixture execution, not just a config inspection.
- 16 new tests (`tests/test_generation_cure_semantics.py`) covering: cure leaving a real future balance, cure never liquidating the contract, future installments preserved after cure, prepayment as distinct from cure, delinquent-> cure -> new delinquency (relapse), impossibility of snapshots after a truly terminal status, full ledger reconciliation (installments/payments/balance/cumulative paid) and coherent DPD before/during/after cure (including a direct call to `credlens.contracts.validation.validate_contracts_strict`), write-off/recovery behavior unaffected, and determinism for the same config+seed.
- A real, pre-existing test bug was found and fixed while validating this phase: `test_monte_carlo_two_seeds`'s cleanup used a substring match (`"2026" in run_dir.name`) that silently deleted unrelated run directories sharing that seed - including this phase's own official demonstration suite runs. Fixed to compute and delete only the exact run ids the test itself created.
- **Analytical warehouse** (`warehouse/`, a dbt-core 1.12.0 + dbt-duckdb 1.10.1 project, both pinned in `uv.lock` under the optional `warehouse` extra - `uv sync --extra warehouse`): raw (source-validated views tagged with run/suite/scenario/seed/scale/generator_version metadata) -> staging (`stg_*`, technical normalization + deterministic composite surrogate keys) -> intermediate (`int_*`: calendar, monthly contract states with cure/relapse/MOB derivation, application->decision->contract linkage, write-off/recovery) -> dimensions (`dim_date`/`dim_run`/`dim_scenario`/`dim_customer`/`dim_channel`/`dim_region`/`dim_policy`/`dim_dpd_bucket`) -> facts (`fct_applications`/`fct_credit_decisions`/`fct_contracts`/`fct_installments`/`fct_payments`/`fct_account_monthly`/`fct_collections`/`fct_writeoffs`/`fct_recoveries`/`fct_macro_monthly`) -> marts (`mart_credit_funnel_monthly`/`mart_portfolio_monthly`/`mart_delinquency_monthly`/`mart_vintage_cohorts`/`mart_roll_rates`/`mart_cure_and_redefault`/`mart_collections_performance`/`mart_writeoff_recovery`/`mart_scenario_comparison`) - 62 SQL models plus 1 seed (63 files total), 185/185 dbt nodes passing (1 seed, 26 tables, 122 data tests, 36 views) against a single run; 197/197 against a full 5-run suite, including the 12 singular tests added after this entry was first drafted.
- Safe source selection (`credlens.warehouse.sources.resolve_sources`): loads only runs with a valid, `completed`, strictly-validated manifest under the generator's own configured output root, explicitly rejects any path under `data/quarantine/`, and only accepts a recognized `contract_version_set`. Selection is always explicit (`--run-id` XOR `--suite-id`), never an implicit "most recent run."
- Cross-run key isolation: every warehouse key is `md5(run_id, natural_id, ...)` (`macros/surrogate_key.sql`), never the bare natural id - proven empirically that 5 CRN runs sharing the same `customer_id` values produce 1000/1000 unique `customer_key` values with zero collisions.
- `credlens warehouse {prepare,build,test,status,query,docs}` CLI command group: `prepare`/`build` take `--run-id` XOR `--suite-id` (argparse-enforced mutual exclusion); `build` invokes dbt programmatically via dbt-core's own `dbtRunner` (no subprocess/stdout-scraping) and writes a build manifest (`data/warehouse/<build_id>/build_manifest.json`) recording build id, database path, included runs, code/dbt/DuckDB versions, source hashes, raw and materialized-model row counts, test results, step durations, an analytical fingerprint, and final status; `test` re-runs dbt tests against an already-built database without rebuilding; `status`/`query` read a prior build's manifest/database; `docs` generates (never serves) the dbt docs site. `--json` available on every read/write command for structured output.
- Analytical fingerprint: a sha256 over each materialized dimension/fact/mart table's exact row count and an order-independent content hash, plus build metadata - deliberately NOT a hash of the `.duckdb` binary file (not guaranteed byte-stable across equivalent rebuilds). Idempotency proven directly: two independent builds from the same suite selection produced byte-identical analytical fingerprints.
- A real determinism bug was found and fixed while proving idempotency: staging models cast every monetary column to `DOUBLE`, and DuckDB's multi-threaded `SUM`/`AVG` over floating point is not associative - two builds from identical inputs produced tiny (~1e-11 relative) but real differences in `mart_portfolio_monthly`/`mart_delinquency_monthly`/`mart_roll_rates`/`mart_vintage_cohorts`. Fixed by casting every monetary column to `DECIMAL(18,2)` in staging (new `macros/money.sql`) - decimal arithmetic is exact fixed-point and thread-order-independent, matching the generator's own `Decimal`-based ledger.
- No new core runtime dependencies: `dbt-core`/`dbt-duckdb` (and DuckDB itself) live in `[project.optional-dependencies].warehouse`, resolved via `uv add --optional warehouse` and pinned in `uv.lock`, never hand-picked.

### Explicitly not included in this phase

A dashboard, a trained/predictive credit score, a web API, an executive report with banking recommendations, profit-based cutoff optimization, causal inference, cloud deployment, and no commits/pushes - see `docs/roadmap.md`.

## [0.5.0] - 2026-07-25

### Added — Performance, counterfactual scenarios, and common random numbers phase (4B)

- **Performance**: profiled (cProfile + coarse `time.perf_counter` checkpoints) the `sample`-scale generator (re-measured at 8.484s on this machine with the unmodified Phase 4A code, not the ~57.3s figure Phase 4A's own report cited under different machine conditions) and applied 4 verified optimizations - bulk `states` construction in `payments.py` (was thousands of separate `groupby`+`to_dict` calls), vectorized canonical table hashing in `manifest.py` (was `DataFrame.apply(axis=1)`), manual month arithmetic in `schedules.py` (verified equivalent to `pd.DateOffset` across 200,000 randomized cases), and head-index installment pruning in `payments.py`. Result: **8.484s → 3.734s (~2.27x)**, `global_content_hash` preserved exactly at both `smoke` and `sample` scale. Two real bugs were found and fixed while doing this (a numpy fixed-width-string NUL-stripping quirk in the hash function, and a pre-existing `next_due_date` inclusive-boundary quirk that a naive optimization would have silently changed) - see `docs/performance_optimization.md`.

No other contract or business rule changed - Phase 4B's quarantine incidents reuse 5 existing business-rule error codes (`PK_DUPLICATE`, `FK_ORPHAN`, `DOMAIN_VIOLATION`, `SNAPSHOT_AFTER_TERMINAL_STATUS`, `DECISION_BEFORE_SUBMISSION`) rather than adding new ones.

## [0.4.0] - 2026-07-24

### Added — Baseline deterministic synthetic-portfolio generator phase (4A)

- `src/credlens/generation/` package: `config` (Pydantic-validated executable configuration, `config/synthetic/baseline.generation.yaml`), `rng` (12 independent `numpy.random.Generator` substreams derived from one `SeedSequence`), `ids` (deterministic, sequential, prefixed, non-CPF identifiers), `population`/`applications` (customers, applications, frozen `application_features`, evaluation-only `fairness_attributes`), `policies`/`decisions` (a synthetic decision score computed only from visible features, never the truth layer), `contracts`/`schedules` (booking + `Decimal`-based reducing-balance amortization, residual-cent-safe), `payments` (the month-by-month ledger simulation - the core of the generator), `allocations` (deterministic fees→interest→principal payment allocation), `snapshots` (DPD/bucket/balance derivation from the in-memory ledger), `collections`/`writeoffs`/`recoveries` (event decision and row construction), `macro` (re-expresses real, already-acquired BCB data - never invents a value), `truth` (the physically isolated synthetic-truth layer), `manifest` (canonical, order-independent per-table/config/global content hashing), `writers` (Parquet output, path-traversal-safe atomic staging→promotion), `validation` (contracts-strict + PII-safety + technical statistical checks), and `orchestrator` (`generate_baseline`, tying every step together in causal order).
- Real CLI commands, replacing the Phase 3 stub: `credlens synthetic generate --scenario baseline --scale {smoke,sample,portfolio} --seed N [--force]` (every other scenario is rejected with `ScenarioNotCalibratedError` before any generation runs), `credlens synthetic validate --run-id <id>`, `credlens synthetic inspect --run-id <id>`, `credlens synthetic manifest --run-id <id>` - all path-traversal-safe.
- Reproducibility, proven (not just claimed): the same `(scenario, scale, seed, config)` produces an identical `generation_run_id` and an identical canonical `global_content_hash` across independent runs; a different seed produces a different one - verified via the real CLI (three real generations in this phase's own validation) and via `tests/test_generation_orchestrator.py`.
- Three mandatory Phase 3 conceptual fixes, completed before the generator was built: (1) `macro_context_monthly` row-level provenance (`source_type`/`source_id`/`is_synthetic` columns + `macro_context_provenance_consistent` rule) so real BCB observations and future synthetic shocks can never be silently conflated - see `docs/adr/0008-macro-context-provenance.md`; (2) removal of the Phase 3 fixture's `DPD=999` sentinel, replaced by a `no_snapshot_after_terminal_status` retention rule and a real, ledger-derived DPD, always - see `docs/adr/0009-dpd-sentinel-removal.md`; (3) `account_monthly_snapshots.cumulative_paid`/`total_balance`/`cumulative_write_off`/`dpd` now reconciled against `installments`/`payments`/`payment_allocations`/`write_off_events` via 4 new financial rules, closing the gap Phase 3 explicitly declared open.
- 6 new business-rule functions (22 → 28 total in `registry.KNOWN_BUSINESS_RULE_CODES`): `macro_context_provenance_consistent`, `no_snapshot_after_terminal_status`, `snapshot_cumulative_paid_reconciled`, `snapshot_balance_reconciled_with_ledger`, `snapshot_write_off_reconciled`, `snapshot_dpd_reconciled_with_installments`.
- `credlens.contracts.validators` now dispatches file reads by the file's own extension (supporting Parquet) rather than solely by the contract's declared `format`, so the same 20 contracts validate both hand-authored CSV fixtures and real generated Parquet output without a schema change.
- The `baseline` scenario blueprint (`config/synthetic/scenarios/baseline.blueprint.yaml`) now has concrete, documented synthetic-assumption parameter values (status `synthetic_assumptions_specified`, a new `BlueprintStatus`) mirroring the executable config; every other scenario remains `requires_calibration`.
- 6 real bugs found and fixed while building and testing this phase's own generator (documented transparently in `docs/synthetic_generation_implementation.md`): an `ALLOCATION_EXCEEDS_PAYMENT` false positive from a missing floating-point tolerance, empty-result tables losing their column schema, a `pd.merge_asof` dtype mismatch on all-empty ledger inputs, a missing `due_date < snapshot_date` filter in the ledger reconciliation, a cross-month payment-reversal bug that broke reproducibility (caught by the determinism proof itself), and `credlens synthetic validate` silently skipping non-`synthetic_operational` tables.
